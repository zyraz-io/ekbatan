## ADDED Requirements

### Requirement: AbstractRepository accepts DatabaseRegistry instead of TransactionManager
AbstractRepository MUST accept a DatabaseRegistry in its constructor, replacing the direct TransactionManager parameter. An optional ShardingStrategy parameter SHALL default to NoShardingStrategy.

#### Scenario: Non-sharded constructor
- **WHEN** a repository is constructed with only a DatabaseRegistry
- **THEN** NoShardingStrategy is used by default

#### Scenario: Sharded constructor
- **WHEN** a repository is constructed with a DatabaseRegistry and a ShardingStrategy
- **THEN** the strategy is used for shard-aware routing

### Requirement: Shard-aware DSLContext resolution methods
AbstractRepository MUST provide overloaded methods for resolving DSLContexts by default shard, by ID, by persistable, or across all shards.

#### Scenario: db() returns default shard primary
- **WHEN** `db()` is called (no args)
- **THEN** the primary DSLContext for `databaseRegistry.defaultShard` is returned

#### Scenario: db(ID) routes to correct shard
- **WHEN** `db(id)` is called with an ID generated by EmbeddedBitsShardingStrategy for shard (0, 1)
- **THEN** the primary DSLContext for shard (0, 1) is returned

#### Scenario: db(PERSISTABLE) routes by persistable's ID
- **WHEN** `db(persistable)` is called
- **THEN** it delegates to `db(persistable.getId())`

#### Scenario: dbs() returns all shard primaries
- **WHEN** `dbs()` is called
- **THEN** all primary DSLContexts from the registry are returned

#### Scenario: readonlyDb() returns default shard secondary
- **WHEN** `readonlyDb()` is called (no args)
- **THEN** the secondary DSLContext for `databaseRegistry.defaultShard` is returned

#### Scenario: readonlyDb(ID) routes to correct shard
- **WHEN** `readonlyDb(id)` is called
- **THEN** the secondary DSLContext for the resolved shard is returned

#### Scenario: readonlyDbs() returns all shard secondaries
- **WHEN** `readonlyDbs()` is called
- **THEN** all secondary DSLContexts from the registry are returned

### Requirement: Shard-aware transaction context methods
txDb() and txDbElseDb() MUST support shard-aware overloads that check the correct shard's TransactionManager.

#### Scenario: txDb() checks default shard TM
- **WHEN** `txDb()` is called (no args)
- **THEN** it checks `databaseRegistry.defaultTransactionManager().currentTransactionDbContext()`

#### Scenario: txDb(ID) checks correct shard TM
- **WHEN** `txDb(id)` is called
- **THEN** it resolves the shard from the ID and checks that shard's TransactionManager for active transaction

#### Scenario: txDbElseDb(ID) falls back to db(ID)
- **WHEN** `txDbElseDb(id)` is called and no transaction is active on the resolved shard
- **THEN** `db(id)` is returned as fallback

#### Scenario: txDbElseDb(PERSISTABLE) falls back to db(PERSISTABLE)
- **WHEN** `txDbElseDb(persistable)` is called and no transaction is active
- **THEN** `db(persistable)` is returned as fallback

### Requirement: Base CRUD methods are shard-aware
Existing add, update, findById, and other base methods MUST use shard-aware DSLContext resolution.

#### Scenario: add() routes to correct shard
- **WHEN** `add(wallet)` is called for a wallet whose ID maps to shard (0, 1)
- **THEN** the insert is executed against shard (0, 1)'s DSLContext

#### Scenario: findById() routes to correct shard
- **WHEN** `findById(id)` is called with an ID that maps to shard (0, 1)
- **THEN** the query is executed against shard (0, 1)'s DSLContext

#### Scenario: Non-sharded repository unchanged behavior
- **WHEN** a repository uses NoShardingStrategy (default)
- **THEN** all operations route to the default shard, identical to current behavior

### Requirement: Batch methods MUST resolve shard from the batch, not default
Batch methods (`addAll`, `addAllNoResult`, `updateAll`, `updateAllNoResult`) MUST use shard-aware `txDbElseDb(PERSISTABLE)` resolved from an entity in the batch — NOT the no-arg `txDbElseDb()` which always returns the default shard. All entities in a batch are guaranteed to be on the same shard (ActionExecutor groups by shard before persisting), so resolving from any entity in the batch is correct.

#### Scenario: addAllNoResult uses shard from batch entity
- **WHEN** `addAllNoResult(wallets)` is called and all wallets map to shard (0, 1)
- **THEN** the batch insert is executed against shard (0, 1)'s DSLContext, not the default shard

#### Scenario: updateAllNoResult uses shard from batch entity
- **WHEN** `updateAllNoResult(wallets)` is called and all wallets map to shard (0, 1)
- **THEN** the batch update is executed against shard (0, 1)'s DSLContext, not the default shard

#### Scenario: Batch resolved from first entity
- **WHEN** a batch method needs to determine the shard
- **THEN** it MUST resolve from the first entity in the collection via `txDbElseDb(domainObjects.iterator().next())`
